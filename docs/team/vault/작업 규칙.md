## 사용자 직접 지시 — 2026-10-05

- 최종 목표는 로스트아크 정보 사이트들의 기능을 하나로 합친 서비스다.
- 판단이 애매한 제품·API 결정은 **로스트아크 공식 홈페이지와 목표 비교 사이트들을 분석**해서 정한다. 같은 테스트 캐릭터(기본 언새늘)로 관찰하고 근거를 `00 공통`에 기록한 뒤, 여러 사이트가 공통으로 택한 방식을 우선 검토한다. 증거 원칙(미검증 점수 비공개)과 프론트 호환성은 유지한다.
- 백엔드 채팅의 진행 안내와 보고는 한국어로 작성한다.
- PR은 검증 후 바로 병합하고 멈추지 않고 다음 작업을 이어간다.
- 이력 저장은 비교 사이트(로아와·클로아·로펙·일로아)처럼 저장·제공한다. 공식 보관 범위 회신을 기다리지 않는다(2026-10-05 사용자 결정). 기존 "관측 저장 기본 비활성" 정책을 대체한다.

- 참고 사이트의 디자인을 그대로 따라 하지 않는다. 법적 문제가 될 수 있으므로 목표 사이트는 기능·정보 구성·사용 흐름을 참고하는 데 쓰고, 화면 구성·배치 수치·색·장식은 LOAKraken 고유 디자인(Apple 라이트 기준·Libraries.dev 오브 모션)으로 새로 설계한다. 다른 사이트의 CSS 값·레이아웃 비율·이미지·문구를 복사하지 않는다. (2026-10-05 프론트 채팅 사용자 지시)
- 위 원칙의 구체화(같은 날 사용자 지시): 화면의 **동작 조건과 구성(정보 배치·탭 구조·갱신 조건·흐름)은 목표 사이트(캐릭터 검색은 일로아)와 최대한 같게** 하고, **시각 표현(색·글꼴·면·장식·모션)만 LOAKraken 디자인**으로 한다. 다른 사이트의 CSS 수치·이미지·아이콘·문구는 복사하지 않는다.

## 사용자 직접 지시 — 2026-10-08

- PM 채팅이 진행 방향·부족한 점·사용자 체감 어색함을 검토한다. 프론트·백엔드 채팅은 **PR을 올리면** PM에게 검토를 요청하고, 판정 후 병합한다. 상세는 [[PM 검토 절차]].
- 디자인 원칙 갱신: 목표 사이트를 **약 90% 그대로 따라간다**. 동작·구성뿐 아니라 익숙한 시각 관례(예: 품질 숫자 배지·글자 크기)도 따른다. 나머지 약 10%만 티 나지 않는 LOAKraken 손질이다.
  - 이미지·아이콘·문구·CSS 파일 원본 복사는 여전히 금지한다.
  - 2026-10-05의 "시각 표현은 LOAKraken 고유 디자인" 지시를 대체한다.

## 자료의 역할

첨부 기준서는 제품·기술·컨벤션의 기준 자료다. 사용자 직접 지시와 문서의 제안·예시를 구분한다. 예시 점수, 비용, TTL, 엔티티 필드가 모두 확정된 구현 계약은 아니다.

SSMBACKEND에서는 기록 방식만 참고한다. 그곳의 읽기 전용 제한, DB 금지, 팀별 조건, 승인 절차는 이 프로젝트로 이관하지 않는다.

## 기록 운영

- 공통은 `00 공통`, 백엔드는 `10 백엔드`, 프론트엔드는 `20 프론트엔드`에 쓴다.
- 각 영역에 현재 작업과 작업 보드를 둔다. 노트 이름에도 영역명을 붙여 중복 링크를 방지한다.
- 날짜별 로그에는 목적, 실제 변경, 검증 결과, 커밋·이슈·PR, 남은 일을 쓴다.
- 완료는 실제 결과로 확인한 항목에만 표시한다. 제안과 미확정 사항은 구분한다.
- 원본은 `raw`에 보존하고 해석·변경 결정은 별도 노트에 쓴다.
- API 키, 토큰, 비밀번호는 문서·코드·로그에 기록하지 않는다.
- 사용자의 기존 변경을 덮어쓰지 않고 작업 시작과 종료 시 Git 상태를 확인한다.

## 성능 우선 — 버벅임·렉 금지 (사용자 지시 2026-10-09, 기본 조건)

애니메이션·3D·차트 등 어떤 효과도 **사이트가 버벅이거나 렉이 걸리면 넣지 않는다.** 모든 프론트 작업의 기본 조건이며 다른 요구보다 앞선다.

| 항목 | 기준 |
|---|---|
| 움직임 | `transform`·`opacity`만 애니메이션한다(GPU 합성). width·height·top·left·box-shadow를 프레임마다 바꾸지 않는다. 높이 펼침은 motion layout 또는 grid-rows 방식 |
| 프레임 | 애니메이션 중 60fps 유지, 50ms 넘는 긴 작업 없음 |
| 지표 | 모바일 중급 기기(CPU 4배 감속) 기준 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하 |
| 번들 | 효과 추가로 늘어나는 첫 로드 JS는 경로당 gzip 30KB 이하. 차트·3D는 동적 import로 따로 불러온다 |
| 화면 밖 | 보이지 않는 요소는 애니메이션하지 않는다(whileInView once). 목록 순차 등장은 앞 12개까지만, 나머지는 즉시 |
| 3D | 화면에 보이고 브라우저가 한가할 때만 불러온다. 탭이 숨거나 화면 밖이면 멈춘다(frameloop demand), 픽셀 비율 상한 1.5 |
| 저사양 | CPU 4코어 이하·메모리 4GB 이하·데이터 절약 모드·`prefers-reduced-motion`이면 무거운 효과를 끄고 정지 화면으로 |
| 반복 | **다른 화면·탭에 갔다가 다시 들어오면 등장 애니메이션을 다시 재생한다**(사용자 지시 10-10). 같은 화면에 머무는 동안 데이터 갱신(시세 1분 등)으로는 다시 재생하지 않는다 |

- 검증: PR마다 Chrome DevTools 성능 측정(CPU 4배 감속)으로 위 지표를 확인해 검토 요청의 "검증" 줄에 적는다. 스킬 `web-perf`·`debug-optimize-lcp`·`chrome-devtools`.
- 판정: 기준을 넘으면 PM-프론트가 **P1**(병합 전 수정). 효과를 줄이거나 빼는 것이 기본 해결책이다.

- **예외(2026-10-09 PM 결정)**: 차트 선 그리기(SVG `stroke-dashoffset`)는 대안이 없어 허용한다. 조건은 한 화면에 차트 3개 이하, 600ms 이하, 화면(탭)에 들어올 때마다 1번(같은 화면에서 데이터 갱신 때는 재생하지 않음), 측정상 느린 프레임이 효과를 끈 상태와 같을 것. 막대 늘어나기는 `clip-path` 대신 `transform: scaleY`(아래 기준점)로 한다. 그 밖의 예외는 측정 결과와 함께 PM 총괄에 요청한다.
- **측정 예외(2026-10-10 PM 결정)**: transform·opacity 외 속성(예: clip-path)도 **CPU 4배 감속 측정에서 프레임마다 다시 그리지 않고(합성), 50ms 넘는 긴 작업이 없을 때**는 담당 PM이 측정값을 PR 판정에 적고 승인할 수 있다(첫 사례 web #263 탭 알약: Paint 회당 4, 긴 작업 최대 42ms).

## 계산 일치 원칙 — 확실하지 않으면 내지 않는다 (사용자 지시 2026-10-09, 같은 날 보완)

목표 사이트들은 같은 값을 보여 주는데 크라켄만 다르고 그 이유를 증명하지 못하면 아무도 크라켄을 쓰지 않는다. 틀린 계산은 만든 비용이 전부 낭비다. 핵심은 "무조건 같게"가 아니라 **"확실한 값만 낸다"**이다.

1. **목표 사이트와 같으면 통과.** 같은 캐릭터·같은 입력으로 그 값을 보여 주는 목표 사이트와 반올림 범위 안에서 같으면 된다.
2. **달라도 크라켄이 맞다고 증명하면 통과.** 사용자 확인(2026-10-09): "같지 않아도 우리 계산식이 정확하다면 그렇게 해도 된다." 증명으로 인정하는 근거:
   - 공식 공지·공식 API·게임 안 표기(툴팁·아이템 사전·캐릭터 정보 화면)
   - 게임 안 실제 결과와의 대조(같은 조건에서 나온 실제 수치)
   - 공식 확률·수치에서 출발한 계산을 계산 검증팀이 독립으로 다시 계산해 일치
   증명이 되면 계산 검증팀과 PM 총괄이 승인하고, 화면에는 막연한 "다를 수 있음" 대신 **구체적 근거**(예: "공식 공지 기준 성공률 3%로 계산, 로아와는 4% 적용")를 보여 준다.
3. **다른데 확실하지 않으면 P0.** 원인을 모르거나 증명이 없으면 병합·공개하지 않는다. "다른 사이트와 다를 수 있음", "1~2%p 다를 수 있음" 같은 막연한 문구로 넘기는 것을 금지한다.
4. **목표 사이트끼리 값이 다르면** 공식 근거로 가린다. 근거가 없으면 가장 많이 쓰이는 사이트(일로아·로아와) 값을 따르고 PM 총괄에 올린다.
5. **검증 방법:** 계산 영향 PR은 계산 검증팀이 목표 사이트 실측값(캐릭터·입력·사이트·확인 시각)과 크라켄 값을 나란히 적은 대조표로 회신한다. 표본은 서로 다른 직업·스펙 5명 이상, 특수 직업(상태 변신·각인 조건) 포함. 모든 행이 "일치" 또는 "불일치 + 크라켄이 맞다는 증명"이어야 승인이다.
6. **데이터 범위 안내는 허용한다.** 공식 API가 주지 않아 생기는 범위 설명(예: "LOAKraken이 확인한 표본 기준 순위", "장착한 칭호만 기록")은 사실을 알리는 문구라 괜찮다. 계산이 틀린 것을 덮는 데 쓰면 안 된다.

## 작은 동작까지 흡수 (사용자 지시 2026-10-10)

- 목표 사이트의 기능은 화면·메뉴 단위만이 아니라 **마우스 올림(hover)·클릭·길게 누르기로 나오는 세부 정보(툴팁·펼침·미리보기)까지** 흡수 대상이다. 예: 캐릭터 화면의 장비·아이템에 마우스를 올리면 상세 툴팁.
- 레퍼런스는 전수표에 작은 동작을 별도 항목으로 적고(`40 레퍼런스/작은 동작 전수표.md`), 흡수 현황에서 기능으로 센다. 담당 PM은 판정 때 작은 동작 누락을 확인한다.

## UI 수정은 스킬 점검 필수 (사용자 지시 2026-10-10)

- 리팩토링·UI 수정·새 화면 PR은 스킬로 점검한다. 설계 전: `apple-design`, `impeccable`(critique·clarify), `ux-heuristics`, `design-taste-frontend`, `ux-copy`. 구현 후: `emil-design-eng`, `animate`, `frontend-a11y`, `web-design-guidelines`, `gstack-design-review`, `web-perf`.
- PR 본문에 "스킬 점검" 줄(쓴 스킬과 고친 점)을 적는다. 없으면 PM-프론트가 반려한다.
