# 팀 구성과 소유권

관련: [[작업 규칙]], [[PM 검토 절차]], [[PM 검토 기록]], [[팀 간 요청]]

## 사용자 직접 지시 — 2026-10-08

- 역할을 세분화해 프로젝트 안에 팀(채팅)을 나눈다. 각 팀은 프로젝트 목표·정책을 따르고 옵시디언에 기록한다.
- 사용자가 승인한 신규 팀은 네 개다: 레퍼런스 분석, QA·테스트, 디자인 시스템, 계산 모델 검증.
- 16개 역할 프롬프트(Reference Analyst … Documentation Writer)는 아래처럼 팀에 나눠 담았다. 파일이 겹치는 역할은 별도 채팅 대신 점검표로 넣었다.

## 공통 규칙 (모든 팀)

1. 시작할 때 [[index]], [[작업 규칙]], [[커밋과 PR 규칙]], [[코드 컨벤션]], 이 문서, [[PM 검토 절차]]를 읽는다.
2. 목표: 로스트아크 정보 사이트 13곳의 모든 기능을 하나로 합친다.
   - 화면은 목표 사이트를 약 90% 따라간다.
   - 이미지·아이콘·문구·CSS 파일의 원본 복사는 금지한다.
3. 판단이 애매하면 공식 홈페이지와 목표 사이트를 같은 캐릭터 **언새늘**로 관찰해 정한다.
4. 증거 원칙
   - 미검증 점수는 공개하지 않는다.
   - 확인할 수 없는 수치는 "추정"으로 표시한다.
   - 실행하지 않은 검사는 "통과"라고 쓰지 않는다. `verification-before-completion` 스킬을 쓴다.
5. 호출 예산
   - 로스트아크 공식 API는 백엔드 공통 90회/분을 공유한다. 조사용 실조회는 최소로 하고, 저장된 표본을 먼저 쓴다.
   - OpenAI는 예산이 약 1만 원이다. 신규 팀은 쓰지 않는다.
6. 저장소 작업
   - 이슈 → develop 기반 브랜치 → 목적별 커밋 → PR 흐름을 따른다.
   - PR을 올리면 담당 PM(프론트·디자인·QA는 PM-프론트, 백엔드·계산 검증은 PM-백엔드. PM 총괄 아님)에 검토를 요청하고, 판정을 받은 뒤 병합한다. 결정·스킬 요청은 PM 총괄로 보낸다.
   - 커밋에 도구 공동 작성자 트레일러를 넣지 않는다.
   - **PR 제목은 이슈와 같은 `[TYPE] 한글`이고, 병합 커밋 메시지만 `<type>: 한글 (#PR)`이다.** 병합할 때 `gh pr merge <번호> --squash --subject "feat: … (#번호)"`로 지정한다(2026-10-09 정정).
7. 작업 트리 분리
   - 다른 팀이 쓰는 폴더(`C:/LOAKraken/loakraken-web`, `C:/LOAKraken/loakraken`)에서 브랜치를 바꾸지 않는다.
   - 자기 작업은 `git worktree add C:/LOAKraken/wt/<팀>-<이슈번호> …`로 분리한다.
   - 개발 서버는 자기 포트를 쓴다.
     - 레퍼런스: 없음
     - QA: 3200번대
     - 디자인: 3300번대
     - 계산 검증: 백엔드 8090번대
   - 통계 수집기는 기본으로 꺼져 있다(#100, develop fe09a92, 2026-10-09). **`STATS_COLLECTOR_ENABLED=true`는 지정된 한 곳에서만 켠다.** 지금은 백엔드팀 8080이다. **#149 병합 뒤에는 로컬 collector 컨테이너(127.0.0.1:8080, 작업 트리 `C:/LOAKraken/wt/collector`)로 바뀐다**(병합한 팀이 이 줄을 고친다). PC와 Docker Desktop이 켜져 있을 때만 도는 임시 방식이다. 다른 인스턴스는 설정하지 않으면 자동으로 꺼진다. 운영 서버가 생기면 지정 위치를 그쪽으로 옮긴다.
   - **PM 검토용 미리보기는 dev 서버가 아니라 `next build && next start`(자기 포트)로 띄운다**(2026-10-09). dev 서버는 미리보기 창에서 HMR 웹소켓이 실패해 새로고침이 반복된다.
8. 소유하지 않은 파일은 고치지 않는다. 필요한 변경은 [[팀 간 요청]]에 적고 담당 팀에 SendMessage로 요청한다.
   - 상대 주소는 `ListAgents`로 확인한다.
   - 결정이 필요한 사항은 PM에 보낸다.
9. 진행 안내와 보고는 한국어로 쓴다.
10. 옵시디언 기록
    - 자기 폴더에 `현재 작업`을 유지한다.
    - 그날 한 일을 `Logs/YYYY-MM-DD.md`의 자기 팀 절에 추가한다.
    - 다른 팀의 절은 고치지 않는다.

- **시각은 추정하지 않는다**(2026-10-09). 전달함·검토 기록·로그에 시각을 적기 전에 `date "+%H:%M"`(Bash) 또는 `Get-Date`로 확인한다. 미래 시각이 적히면 대기 시간 판단과 자동 점검이 틀어진다.

## 옵시디언 기록 규칙 (사용자 지시 2026-10-08)

- 각 팀은 **자기 폴더에만** 기록한다. 필요한 폴더나 하위 폴더가 없으면 새로 만든다.
  - 하위 폴더는 기존 번호 체계를 따른다: `02 현황`, `03 자료 분석`, `04 설계`, `05 검증`.
- 폴더마다 `<팀> 현재 작업.md`를 둔다. 작업을 시작하고 끝낼 때 갱신한다.
- **날짜별 로그는 팀마다 따로 쓴다(2026-10-10부터).** 파일은 `Logs/YYYY-MM-DD/<팀>.md`다(예: `Logs/2026-10-10/백엔드.md`). 폴더나 파일이 없으면 만든다.
  - 이유: 한 파일(`Logs/YYYY-MM-DD.md`)을 10개 팀이 같이 쓰다 보니 다른 팀 줄이 남의 절에 섞이는 일이 세 번 났다(10-09).
  - 팀 파일 이름: PM 총괄, PM-프론트, PM-백엔드, 프론트, 백엔드, 레퍼런스, QA, 디자인 시스템, 계산 검증, 배포·운영, 성장 도구.
  - 2026-10-09까지의 로그는 기존 `Logs/YYYY-MM-DD.md`에 그대로 둔다.
  - (이전 규칙) 날짜별 로그는 `Logs/YYYY-MM-DD.md`의 자기 팀 절에만 추가한다.
  - 쓰기 전에 다시 읽고 이어 쓴다. 다른 팀 절은 고치지 않는다.
- 공용 문서 수정 범위
  - `index.md`, `00 공통`, `30 PM`의 규칙 문서는 PM 총괄이 관리한다.
  - [[팀 간 요청]]은 자기 행만 추가·갱신한다.
  - [[PM 검토 기록]]은 PM들이 판정 행을 추가한다.

|---|---|
| 프론트엔드 | `20 프론트엔드` |
| 백엔드 | `10 백엔드` |
| PM 총괄 | `30 PM` |
| PM-프론트 | `30 PM/프론트` |
| PM-백엔드 | `30 PM/백엔드` |

## 팀 간 흐름

```
레퍼런스 ─(기능 차이 목록)→ PM ─(우선순위)→ 프론트/백엔드
레퍼런스 ─(크기·색 실측)→ 디자인 시스템 ─(디자인 값·공통 부품 PR)→ 프론트
계산 검증 ─(검증 표본·기대값)→ 백엔드 ─(계산 API)→ 프론트
QA ─(재현 실패 테스트가 붙은 이슈)→ 담당 팀 ─(수정 PR)→ PM 검토
```

## 스킬 요청 (사용자 지시 2026-10-08)

- 팀이 필요한 스킬을 찾으면 직접 설치하지 않는다. **PM 총괄에 SendMessage로 요청**한다.
  - 요청 형식: `[스킬 요청] 스킬 이름·출처(owner/repo@skill), 쓰려는 작업, 이미 있는 스킬로 안 되는 이유`
- PM 총괄은 아래를 확인한다.
  - 출처 신뢰도(설치 수, 관리 주체)
  - SKILL.md와 스크립트 내용(외부 전송, 원격 패키지 실행, 훅)
  - 기존 스킬과의 중복
- 필요하다고 판단하면 PM 총괄이 전역 설치하고 요청한 팀에 알린다. 설치하지 않으면 이유와 대안을 회신한다.
- 설치하거나 거절한 결과는 [[스킬 요청 기록]]에 남긴다. 팀은 헌장의 "사용할 스킬"에 추가할 스킬을 회신받아 쓴다.
- 자동 실행 훅이 들어 있거나 다른 채팅의 동작을 바꾸는 플러그인은 PM 총괄이 사용자에게 먼저 확인한다.

## 전달함 (2026-10-09)

- 세션 간 메시지는 **사용자 입력 없이 10건을 넘게 보내면 자동으로 막힌다.** PM-프론트·PM-백엔드처럼 사용자가 직접 입력하지 않는 채팅은 한 번 막히면 계속 막힌다. 그래서 10-09에 PM-백엔드 판정이 몇 시간씩 밀렸다.
- 그래서 팀 간 요청·결정·판정은 **옵시디언 `30 PM/전달함/<받는 팀>.md`에 한 줄로 적는 것을 기본**으로 한다. SendMessage는 받는 팀을 깨워야 할 때만 짧게 보낸다. 예: "전달함에 판정 3건이 있습니다".
- **모든 팀은 작업을 시작할 때와 끝낼 때 자기 전달함을 읽는다.** 처리한 줄은 `- [x]`로 바꾸고 결과를 적는다.
- 메시지가 막히면 전달함에만 적고, 나중에 PM 총괄 순회 점검 때 깨운다.
- 처리한 `- [x]` 항목은 PM 총괄이 주기적으로 `30 PM/전달함/보관/<팀>.md`로 옮긴다. 전달함에는 미처리 항목만 남긴다(매번 읽는 분량을 줄이려고, 2026-10-09).

## 자동 순회 점검 (2026-10-09)

- **보고서는 PM 총괄이 최종 점검한다**(사용자 지시 2026-10-09). 자동 점검은 팀을 직접 깨우지 않고 보고서와 "깨우기 후보"를 PM 총괄 전달함에 제출한다. PM 총괄이 확인한 뒤 깨우기·결정을 진행한다.
- **한도 복구**: 예약 작업 `loakraken-limit-resume`이 5시간 한도 초기화 3분 뒤 실행돼, 한도 오류로 멈춘 세션만 깨우고 다음 초기화 시각으로 다시 예약한다. 크레딧·추가 사용량 설정은 하지 않는다(사용자 지시).
- 사용자 요청으로 예약 작업 `loakraken-team-patrol`을 만들었다. **4시간마다(0·4·8·12·16·20시 17분)** 실행된다(2026-10-09 토큰 절약으로 2시간 → 4시간).

## 담당 PM은 대기열을 비울 때까지 (사용자 지적 2026-10-10)

- 사용자 지적: 담당 PM이 한 건 처리하고 멈춘다.
- 담당 PM(PM-프론트·PM-백엔드)은 한 건을 끝낸 뒤 턴을 끝내기 전에 **반드시 다시 확인**한다: ① 자기 전달함의 `- [ ]` ② 자기 저장소의 열린 PR 중 판정이 없거나 새 커밋이 올라온 것(`gh pr list --state open`) ③ CI가 끝나 병합 요청이 필요한 것. 남은 게 있으면 이어서 처리하고, **세 가지가 모두 비었을 때만** 멈춘다.
- 멈추기 전 마지막 줄에 "대기열 비움(전달함 0·판정 대기 PR 0)"을 남긴다.
- 사용자가 PM 세션에서 `/loop`를 켜 두면 일정 간격으로 이 확인을 반복한다(권장 20분).

## 넘김은 "파일 + 깨우기" 한 쌍, 일하는 팀도 대기열을 비울 때까지 (사용자 지적 2026-10-10 19시대)

- 사용자 지적: 프론트·백엔드·PM-프론트·PM-백엔드가 서로 소통하며 이어 가지 않고, 사용자가 하나하나 "진행해"라고 해야 움직인다.
- 원인: 10-09에 메시지 한도(사용자 입력 없이 세션당 10개) 때문에 넘김을 전달함 파일로 바꿨는데, **파일만 쓰고 상대를 깨우지 않는 경우**가 생겼다. 파일은 아무도 깨우지 않는다. 받는 쪽은 자기 턴이 끝나면 다음 메시지가 올 때까지 멈춰 있다.
- 규칙 1 — **넘길 때는 항상 둘 다**: 상대 전달함에 적고 → 바로 SendMessage로 한 줄 깨우기("전달함 HH:MM 확인"). 판정·요청·PR 올림·재베이스 완료·병합 완료 모두 해당.
- 규칙 2 — **일하는 팀(프론트·백엔드·디자인 시스템·성장 도구)도 턴을 끝내기 전에** 자기 전달함과 자기 열린 PR(판정 반영할 것, 충돌, CI 실패)을 다시 보고, 남은 게 있으면 이어서 한다. 다 비었을 때만 "대기열 비움"을 남기고 멈춘다.
- 규칙 3 — PR을 올리면 담당 PM을 반드시 깨운다. PM은 판정 후 작성자를 반드시 깨운다. 병합 후 다음 순서 작업이 있는 팀을 깨운다.
- 메시지 한도가 걱정되면 깨우기를 한 줄로 짧게 하고 여러 건을 한 메시지에 묶는다. 한도에 걸리면 PM 총괄 전달함에 적어 사용자에게 알린다.

## 패치마다 개발자 노트(패치노트) 작성 (사용자 지시 2026-10-10)

- 운영 배포(master 릴리스)마다 사용자용 패치노트를 쓴다. 위치: `30 PM/개발자 노트/패치노트 vX.Y.Z.md`. 형식은 [[패치노트 v0.2.0 (초안)]]을 따른다: 인사 → 새로운 기능 → 개선 → 수정 → 삭제 → 준비 중 → 맺음.
- 담당: **배포·운영**이 릴리스 PR을 만들 때 그 릴리스에 들어간 PR 목록(develop..master)으로 초안을 쓰고, PM 총괄에 깨우기. PM 총괄이 다듬어 확정하고 사용자에게 보여 준다.
- 쓰는 말: 사용자가 보는 글이다. PR 번호·코드 이름·팀 이름 대신 화면에서 보이는 변화로 쓴다. **다른 사이트 이름 금지**(작업 규칙). 운영에서 숨긴 기능은 "준비 중"에만 적는다.
- 릴리스 점검표에 "패치노트 확정"을 넣는다. 확정 전에는 배포 승인을 요청하지 않는다.
